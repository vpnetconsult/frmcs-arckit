# Pivot notes — what the ibn-core intent stack can carry for a rail end-to-end scenario

**Date:** 2026-09-20 · **Pivot state:** `current/` at 530 rows (`E-2026-09-19-50` last); baseline `2026-09-19_2321`. · **Siblings:** `pivot-notes-2026-09-19-ontology.md` (the layers: ontology and law), `pivot-notes-2026-09-20-path-booking-ontology.md` (the entities of a multi-IM path), `pivot-notes-2026-09-15-knowledge-plane.md` (what the agents reason over). · **Act:** `14-next-acts.md` A14.
**Purpose:** read one existing intent-based-networking build — the ibn-core knowledge-graph architecture as drawn on 2026-09-20 (local kind cluster, two peers, one core) — component by component, and say for each what a rail scenario would put through it, what the register already holds for that, and what is missing. The point is to turn ADR-002 rule (xi) from a paragraph into a build target with a named host.

**Outcome anchor:** *safe, continuous rail operations.* A stack like this is where an infrastructure manager's intent to its bearer would actually be written, decomposed and reported on. If the rail vocabulary cannot pass through it, the intent stays prose and the 23-June record stays free text.

**Guardrail:** oversight, not control. Every run below ends in a report or a proposal to a human. Class-4 actions are never expressed as an intent at all (ADR-002 item 9, 28.312 reading).

**Source of the diagram:** a screenshot held locally (`Downloads/Screenshot 2026-09-20 at 4.07.15 PM.png`), titled *"ibn-core Knowledge-Graph Architecture — local kind cluster + two peers, one core (September 2026)"*. It is a working drawing of a private build, not a published specification; nothing here is evidence about any operator or vendor. **Its `ADR-007`, `W1/W3/W5` and `ARC-004-BENCH-001` labels are ibn-core's own numbering and are not this register's ADR-007.**

## 1. The setup, as drawn

- **business-intent-agent** (BSS peer, public): TMF921 v5 API ingestion → intent processor with an LLM client → an MCP adapter seam marked as the open-core boundary → orchestration. An in-memory knowledge store; telemetry to OTLP.
- **resource-intent-agent** (peer 2, private): 3GPP TS 28.541 NRM (`NRCellDU`, YANG) → RML mappings → RML engines (morph-kgc benchmarked, a hand-rolled mapper validated, RMLMapper retry pending) → N-Triples out; a planned named-graph upsert into Fuseki.
- **kind cluster, namespace intent-platform:** knowledge-graph-mcp, bss-oss-mcp, customer-data-mcp (all MCP over HTTP); Neo4j 5.26 CE with n10s holding a TMF620 product-catalog graph (native Product · Bundle · Intent · Segment; RDF `tmf620__ProductOffering…`; SHACL shapes compiled); Redis as single source of truth / persistence.
- **kind cluster, namespace resource-platform:** Apache Jena Fuseki 5.1.0 (TDB2, `/ds`), currently empty, standby for a Phase-2 named-graph DELETE/INSERT.
- **Semantic validation:** `tmf620-shacl-shapes` active in n10s (four violations reported: two products missing price fields); `tio-shacl` a candidate (Ericsson / MIT, TIO v3.6.0) behind a gate option.

Read against `pivot-notes-2026-09-19-ontology.md` §1: the setup lives entirely at **L2′** (TM Forum) and **L2** (3GPP SA5), the two layers where machine-readable vocabularies exist and no law does. It has no L7 content. That is exactly the shape of the void the ontology note describes, seen from the other side.

## 2b. The chain, bottom-up: 3GPP common core → FRMCS → on-board TOBA → all-IP → one network slice

*(Added 2026-09-20, later sitting; E-2026-09-20-04. The chain names, for each layer, what binds it, which held text says so, what it contributes to the rail E2E, and where it lands in the ibn-core setup. The point of reading it bottom-up is that the "slice" everyone puts on the slide is, in the held FRMCS text, a single default slice — and that changes what the intent targets.)*

| Layer | Held text | What it says that matters here | Where it lands in the setup |
|---|---|---|---|
| **3GPP common 5G System** | TS 23.501 V20.2.0 + 23.502 (E-2026-09-19-05, read for 5.15 / 5.16 / 5.21.2 / 5.22 / 5.33.2 / 5.40) | No rail clause; rail is an MCX tenant with priority hooks (ARP/5QI, MPS). **Slicing (5.15):** a slice is "a logical network that provides specific network capabilities and characteristics"; identified by **S-NSSAI = SST (8 bit) + optional SD (24 bit)**; standardised SSTs 1 eMBB · 2 URLLC · 3 MIoT · **4 V2X** · 5 HMTC · 6 HDLLC · 7 GBRSS (Table 5.15.2.2-1); the UDM subscription carries at least one **default S-NSSAI**, the NSSF/AMF select the serving slice at registration. **Detection of an AMF failure is unspecified** (5.21.2.3); **everything that makes redundancy real is the operator's** (5.33.2 NOTE 2); disaster roaming (5.40) covers a RAN disaster only. | The resource-intent-agent's TS 28.541 NRM is the management view of exactly these NFs — the held IOCs (E-2026-09-19-30) include `AMFSet`, `NSSFFunction`, **`NetworkSlice`, `NetworkSliceSubnet`, `ServiceProfile` (with `availability` % and `survivalTime`), `SliceProfile`**, each carrying the 28.622 states. These are the DNs the RML mappings would emit as N-Triples. |
| **FRMCS profile of that core** | UIC SRS AT-7800 **v2.1.0 §13 "Network slicing"**, read in full 2026-09-20 (E-2026-09-20-04) | **Slicing is reduced, not exploited.** §13.3.1.4 *"Network slicing shall be reduced for FRMCS to use a single Default S-NSSAI"* (M-V3); §13.3.1.9 the Default S-NSSAI uses the **3GPP-standardised SST value "4" (V2X)** (M-V3, editor's note: a railway-specific SST "under investigation"); §13.3.1.3 **no Slice Differentiator**; §13.3.1.6 one default DNN, default flag, NSSAA indication in the UDM subscription; §13.3.1.7 in a VPLMN the home UDM provides the default S-NSSAI only; editor's note after 13.3.1.5: *"Usage of additional S-NSSAI is out of scope for FRMCS V2"*; **§13.3.1.10 *"The Default S-NSSAI for MNO connectivity shall be different"***; and an editor's note under §13.1 that whether FRMCS needs the slicing NAS protocols at all "is to be confirmed, even if network slicing is not implemented by FRMCS Operators". **So: one slice per FRMCS transport domain; the class A–C service differentiation is QoS and priority *within* it (SRS §14, 23.501 5.22), not slice-per-service.** | The IM's intent has **one** slice object to target per transport domain: the FRMCS `NetworkSlice` (Default S-NSSAI) and its `ServiceProfile`. Per-service expectations (REC, group call, ETCS data) attach to QoS profiles inside it, not to separate slices. |
| **On-board TOBA** | TOBA-7510 v1.0.0 (Table A2 index 99; E-2026-09-04-20, E-2026-09-20-03) and v2.1.0 (E-2026-09-19-19) | Applications reach the system **only via OBAPP** (M); the OBAPP Service Session **"shall transparently carry any IP based protocol"** of a locally bound application (M); wired connectivity is Ethernet (M); the Gateway Function distributes user-plane data over the FRMCS Radio Modules by the application's QoS and priority (Application Profiles, §7.5); the FRMCS Radio Module is a 3GPP UE (power class 1 in n100/n101, TS 38.101-1 — ADR-013 constraint 5). **The on-board never chooses a slice per application:** application-driven domain selection is "excluded by the principle of decoupling" (v1.0.0 §7.4, deleted in V2); the UE's S-NSSAI is subscription data (UDM/SIM), and in V2 the on-board reports transport-domain connected/disconnected with a reason (M / M-V3, §7.9.3.6.6). | The on-board is where the rail vocabulary's *identity* lives (functional alias, engine number as the addressable identifier — TOBA-7510 §7.1) and where the OTLP-style O&M data of §7.6 originates (logs classified Information → Critical; faults per interface; QoS profiles used; apps registered). It is the source of the telemetry.ts feed for a rail E2E-2 replay, and the object ADR-013 stage 2 fits. |
| **All-IP end to end** | SS-037-3 v4.0.0 as read in the CTO-Council report (E-2026-09-20-02); SUBSET-146; TOBA-7510 §7.7 | ETCS over FRMCS is IP end to end: the on-board addresses the RBC by FQDN `id<ETCS-ID>.ty<type>.cc<NID_C>.ertms` over OBapp, TLS per SUBSET-146; voice is MCX over IP; GSM-R's circuit-switched and ISDN interfaces retire once every vehicle on a track is FRMCS-capable (report §6.3). **The QoS the railway experiences is measured on an IP path with defined end-points** — SRS §14.1.3–14.1.4: the application E2E path = the FRMCS E2E path + the external IP portions. | This is the path the intent's expectations must be written against: an IP E2E path per application with a QoS profile, not a "bearer". It is also why the CTO report's adapter vehicles (Solution D) exist — to give a Baseline 3 Euroradio an IP session it cannot open itself. |
| **The network slice, as the management plane knows it** | TS 28.541 (`NetworkSlice` / `NetworkSliceSubnet` / `ServiceProfile` / `SliceProfile`), TS 28.312 intent, TMF921 (E-2026-09-19-30/-06/-34) | One `NetworkSlice` (the FRMCS Default S-NSSAI) composed of `NetworkSliceSubnet`s (RAN, core, transport), with a `ServiceProfile` carrying availability, latency and survival time. 28.312 and TMF921 intents target these DNs; TR290's `icm:` expectations attach to them. **On the public-operator path (path-booking Relation C) the S-NSSAI is a *different* one in the MNO's PLMN (SRS §13.3.1.10) — the slice boundary is the administrative boundary.** Slicing is therefore where the *MNO-side offer* is defined (a TMF620 product characteristic, GSMA NEST ↔ SST mapping per 23.501 NOTE 2 — NG.116 not held), not where FRMCS differentiates its own services. | **The corridor intent of E2E-1 decomposes to three things:** the FRMCS slice's `ServiceProfile` expectations · the per-application QoS profiles inside it · the list of `NRCellDU`s covering the `era:SectionOfLine`s (the rule-(x) operator-side term of §4 item 3). The MNO offer of E2E-3 is a *second* slice in a *second* PLMN, expressed as a product, checked against the parity characteristics. The border of the path-booking note (ENIR hub, B19) is an inter-PLMN transport-domain transition the on-board only *reports*. |

**What this corrects.** The common description — an unattributed search/AI summary supplied to this sitting on 2026-09-20, and before it the DVF/Accenture "Finnish model" position (E-2026-06-24-08, B) — says rail operators isolate mission-critical command-and-control traffic in dedicated URLLC slices (SST 2) apart from passenger broadband and maintenance data, selected by the NSSF at train registration. **The held primary text says otherwise on every one of those points:** FRMCS V2/V3 uses one default S-NSSAI with **SST 4**, not 2; no additional S-NSSAI in V2; no slice differentiator; the on-board does not select a slice per application; the isolation from passenger broadband is a different PLMN or a different S-NSSAI on the MNO side, not a rail slice inside a shared one. "URLLC slice for FRMCS" appears in no held primary text. The summary stays where it belongs — tier D, orientation only — and the SST-2 claim is not carried anywhere in the register.

**Bounds.** SRS §13 is marked M-V3 throughout — a V3 obligation (Sep 2027, C2), with V2 silent on whether operators implement it; the SST-4 choice carries an editor's note; 28.541 is the vendor-neutral model and real cores expose vendor extensions; the register does not hold GSMA NG.116 (NEST) or TS 23.003 §28.4.2 (S-NSSAI format) and does not need them for any position.

**Validated against the MORANE-2 programme (2026-09-20, on request).** Everything the register holds from or about MORANE-2 — the mid-term conference brochure and the CORDIS record (E-2026-09-17-02/-05), deliverable D5.1 (E-2026-09-17-03), the spec map (E-2026-09-17-01), the S+D and UNIFE accounts (E-2026-07-02-15, E-2026-08-02-06), the mid-term news item (E-2026-09-06-06) — contains **no slicing content at all**: zero occurrences of "slice" or "S-NSSAI". The programme's stated scope is 5G SA cores with IMS/SIP, RMR-band radios, TOBA on-board, MCX interoperability across three vendor labs, and cross-border operational testing from 2027. Its test cases are built to FRMCS v2.2 (not held, A7/B1), so whether they exercise SRS §13's single-default-S-NSSAI rule is unknown — but nothing MORANE-2 has published describes per-service rail slices either. The only held instance of a slice in rail use is 5G-RACOM's **public** path: Vodafone via a research network on a dedicated slice with N6-only interconnection (E-2026-07-02-21, A/C) — the MNO-side slice of SRS §13.3.1.10, not a rail slice inside FRMCS. The phrase "the stream-C FRMCS/5G slice" at E-2026-08-02-10 is the register's own loose wording for ETSI Plugtests test stream C (FRMCS over 5G) and is not a network slice. **Verdict on the supplied idea: not usable as stated; usable once inverted — one FRMCS slice, service classes by QoS inside it, the public operator on its own S-NSSAI.**

## 4. What does not exist and must be built first

1. **The rule-(xi) rail extension model as one Turtle file** — functional alias, REC, the class A–C catalogue, the RINF radio terms of rule (ix), each an `imo:IntentExtensionModel` specialisation with `era:` IRIs as `icm:target`s. Everything in §3 waits on it. → **A14.**
2. **The ERA graphs loaded into Fuseki with per-graph provenance** (`prov:`, `dcterms:issued`, a last-verified date). A load step, not a build step; the files are held.
3. **One operator-side term joining a cell to a section of line.** The path-booking note found the same shape of gap for the path itself: messages have classes, the allocated path has none. **Added 2026-09-20 (§2b):** and one more, joining the FRMCS `NetworkSlice` DN (the Default S-NSSAI of SRS §13) to the transport domain it serves — so that a corridor intent can name the slice whose `ServiceProfile` it constrains and the cells that realise it, in one graph.

## 5. What this says for the register

- **Rule (xi) now has a host.** Until today it was a paragraph in ADR-002 with no place to be validated. A TMF921-fronted stack with a Jena store and a SHACL slot is that place, and it exists as a private build.
- **The void of the ontology note is visible from below.** The setup holds L2′ and L2 vocabularies and nothing above; the register holds L7 vocabularies and nothing between. The extension model is the only object that touches both.
- **The guardrail becomes a unit test.** "Class 4 is never an intent" is checkable at the intent processor. That is stronger than any wording in ADR-002.
- **No decision moves.** This note names a build target; it does not change a position. The evidence row, if one is logged for the screenshot, is informational (`NO DECISION MOVED — a private working drawing, not a source about any operator`).
