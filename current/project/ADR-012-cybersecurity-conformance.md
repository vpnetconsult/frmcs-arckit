## Context

The engagement's security dimension was thin — a threat note in ADR-001 §1.8 and the SS7/probe thread (P1/Latro). The VDB CRA-Leitfaden (E-2026-07-01-05, tier B) surfaced the cybersecurity-**regulatory** dimension; primary-law verification (E-2026-07-01-06, tier A) confirmed it as **binding, datable law**, not a proposal.

Two regimes bite:

- **CRA — product side.** Every FRMCS "product with digital element" — 5GC, MCX/IMS core, cab radios, dispatcher terminals — is in scope, **and so is the agentic-oversight layer, which is itself software**. CRA requires secure-by-design, vulnerability handling over a **declared support period**, SBOM, coordinated vulnerability disclosure, and conformity assessment.
- **NIS-2 — operator side.** DB InfraGO is an essential entity in the **Transport** sector (Annex I): Art 21 risk-management measures + Art 23 incident reporting (24 h / 72 h / 1-month).

The load-bearing tension: **CRA mandates security updates over a support period; railway authorisation (Zulassung) demands stability.** Every security update to a live, authorised, safety-critical product is a *change* — it must preserve **Rückwirkungsfreiheit** (freedom-from-interference) against the safety case and pass change-control. This is the **security analogue of the 23-June change-on-live-legacy lesson**: an ungoverned change to a live element caused the outage; an ungoverned security update is the same hazard with a security trigger.

Security ≠ Safety (the CRA-Leitfaden is explicit), but they **couple**: an unpatched vulnerability can become an availability/safety event, and — per the incident's cause-agnostic detection lesson — a fault a component does not self-report includes a **compromise** it does not self-report.

## Decision

Adopt CRA + NIS-2 conformance as a **first-class, governed dimension** of the transition and the oversight layer, reusing the existing ADR-004 / ADR-007 / ADR-011 machinery rather than a parallel security process:

1. **CRA scope + procurement gate.** Treat every FRMCS PDE **and the agentic-oversight layer** as in-scope: secure-by-design, vulnerability handling over a **declared support-period end date**, SBOM, CVD. Procurement (R8) requires manufacturer **CRA evidence** (SBOM, security-update + support-period commitment, CVD contact) as a bid condition — which also discharges **PR13** (proprietary opacity / vendor-fix dependency). **⚠️ AND MODEL PROVENANCE EVIDENCE, ALONGSIDE THE SBOM (added ARB-2026-09-17 R2, closing Q-18; E-2026-09-15-14):** for **(a)** any learned component of the agentic-oversight layer and **(b)** any FRMCS PDE that ships a trained model — **model identity and version · training-data provenance and licence · evaluation record against the declared ODD (ADR-010 item 5) · weight-update mechanism and window · CVD contact for model vulnerabilities.** **Format expressly unspecified**: the register holds no standard model-BOM profile, and a bid condition naming a format nobody can uniformly produce is the size filter minuted at ARB-2026-09-06 R4; when a format is on file, adopting it is an implementation item. **First candidate on file (E-2026-09-19-08, 2026-09-19): 3GPP TS 28.105's `MLModel` IOC and model registration (§6.4.1.2.3) — a normative, vendor-neutral carrier for the identity / version / capability fields, already produced by any 5G vendor implementing AI/ML management; training-data provenance, licence and the ODD-referenced evaluation record remain outside it. Narrows the "unspecified" to the three fields 3GPP does not carry; does not adopt.** The size-filter consequence of the requirement itself is accepted and minuted (ARB-2026-09-17 R2), with ADR-013 constraint 3's supported-variant obligation applying. ADR-002 rule 2 carries this as its sixth condition by cross-reference. Like every clause in this gate, it is evidence to build to; it discharges no conformance.

⚠️ **THE GATE NOW CITES THE SECTOR'S OWN CLAUSES INSTEAD OF THE REGISTER'S PARAPHRASE (added ARB-2026-09-06 R2 and R4, closing Q-12 and Q-13).** **DESIGN REQUIREMENTS:** `SP-SEC-Tax-2-2` — **TSI requirements are directly derived from IEC 62443-3-3**; `SP-SEC-Tax-2-8` — **FRMCS is a Wireless Component**, carrying **IEC 62443-4-2 NDR 1.6, NDR 1.6 RE1, CR 2.2 and CR 2.2 RE1** (the first clause-exact security requirements this register holds that attach to FRMCS radio equipment by name). **SUPPLIER QUALIFICATION, as verifiable bid conditions:** supplier **ISO 27001** for the development organisation and **IEC 62443-4-1 minimum ML 3**; service provider **ISO 27001 + IEC 62443-2-4 minimum ML 3** (ML 3 = CMMI Level 3); **personnel background checks across the whole lifecycle**; a **single security point of contact**. **SUPPLY CHAIN:** **tamper-evident transport seals**, specified against a documented risk assumption **communicated to the customer before delivery**, with **transport-step tracking** including means of transport, storage time and location. ⛔ **THE CEILING, AND IT BINDS EVERY CLAUSE ABOVE: the release note states *"cybersecurity certification aspects and EU CE conformity requirements are not included in this version of the specifications."* These are requirements to BUILD TO. This gate may demand them; it may NEVER treat them as discharging conformance.** ⚠️ **A CONSEQUENCE MINUTED RATHER THAN DISCOVERED LATER: ISO 27001 plus CMMI ML 3 hard-codes a SIZE FILTER. E-2026-08-19-13 measured security maturity correlating with organisation size (r = .42), and ADR-013 constraint 3 requires a supported variant for operators without an in-house security function. This clause will exclude small suppliers and small EVUs from conforming supply — possibly the right answer for safety-relevant procurement, but a distributional choice made by a technical clause.** ⛔ **TWO PROVISIONS WERE PUT TO THE BOARD AND REJECTED, recorded so they are not re-proposed: `Tax-2-13` (all in-scope systems are essential-function) is EU Rail's claim about ITS OWN scope and would CONTRADICT ADR-004's construction that the advisory domain is not essential-function — recorded as an external claim to test, never a premise; and `Tax-2-6` (supplier-side IT/OT DMZ border) was rejected as a connection to the operator-side on-premises-cloud rule on the Q-7 precedent — two arrangements sharing a principle, not one rule governing both.**

2. **Security updates are changes — govern them under ADR-011.** A CRA security update to a live safety-carrying element is a **Class A/B change**: CSM-RA Art 4(2) significance test, inactive-redundancy-only, maintenance window, pre-change test gate (ADR-007 failover injection + canary-by-segment), per-change safety-impact analysis at the SIL-4 boundary (ADR-004). **No security update bypasses change-control on urgency** — instead define an **expedited-but-still-gated** path for actively-exploited vulnerabilities (CRA Art 14).

3. **Preserve Rückwirkungsfreiheit (ADR-004).** Security functions and updates must not interfere with the SIL-4 safety kernel; the EN 50129 freedom-from-interference / composition analysis is the **shared boundary** for both safety changes and security updates.

4. **NIS-2 into the operator SMS.** Art 21 risk-management measures + Art 23 reporting (24 h / 72 h / 1-month) embedded in the operator's Safety/Security Management System; align the reporting chain with **CRA Art 14** (manufacturer) so a vulnerability/incident is reported once, correctly, to the right authority (BSI / CSIRT). **⚠️ AND EVERY SECURITY PROCEDURE ON A SAFETY-RELEVANT RECOVERY PATH IS BOUNDED (added ARB-2026-09-17 R1, closing Q-17): for each obligation enumerated under item 5, the SMS states a TIME BOX and the NAMED AUTHORITY who may proceed with recovery without completing it.** The register requires that a bound exist and be owned; **it does not set the number** — that is the operator's risk decision under CSM-RA, and a register without operational data has no basis to set it. *Wire form (E-2026-09-19-37, TM Forum TMF921A v1.1.0): where the recovery step is mediated by the oversight layer, the bound is the **response timeout in the Judge Intent Notification** and the authority is the **intent owner** who answers with the Preference Intent; the number the operator sets is that timeout, and its expiry must fail safe.* Expressly *not* decided: that any such gate be removed, shortened or bypassed — failing over during an actual compromise can propagate it. What is indefensible is an *unbounded* gate on a recovery path; ADR-007 item 3's procedural-gate injection class is the test that the bound is exercised, not merely written.

5. **Independent detection covers security too (ties PR5/PR11).** The out-of-band monitoring that detects silent faults (ITU-T Q.752 probes, E-2026-06-30-03) feeds security event detection (SIEM / IDS) — the same "don't rely on a component to self-report" principle applies to a compromise as to a silent fault. **⚠️ AND WHAT DETECTION OBLIGES IS ENUMERATED (added ARB-2026-09-17 R1, closing Q-17; E-2026-09-15-01): every security obligation that stands on a safety-relevant recovery path — between a detected event and an authorised recovery action — is listed as an adverse effect on essential functions, with its mitigation, in the form of `SP-SEC-SuppEssFunc` (E-2026-09-05-13).** The founding instance: under DB's own rules for the 23-June scenario, staff had to exclude a cyberattack *before* switching manually to the redundancy that had not engaged — a security control that became an availability cost, unlisted and unbounded. The bound on each such procedure is the operator's, at item 4. The instrument is the sector's own and is named in this ADR for the first time here. **Machine-readable form (E-2026-09-19-40, TM Forum TR292I Security Ontology v4.0.0 as specified in arXiv 2605.27743, Ericsson): a `sec:SecurityExpectation` (extending `icm:Expectation`) carrying `sec:impactOnResource` / `sec:impactValue` / `sec:performanceMetric` is the same listing as an `SP-SEC-SuppEssFunc` entry — the control, the essential function it burdens, the cost — expressed as an intent expectation the oversight layer can reason over; the cyber-exclusion gate of 23 June would be a `sec:MitigationCapability` whose `sec:impactValue` on train-radio availability is the ≈2 h it added.** **What the record of such a path consists of is now also named, from the specs (E-2026-09-19-11, read 2026-09-19): at the MC layer, TS 22.280 §6.15.4 obliges the MC service to log per-communication metadata (time, MCX user ID, functional alias, group, location, end reason, type, success/failure), the non-communication activities (emergency alert/cancel, registration state change, overridden event, affiliation and functional-alias changes, regroups), failed authorisations — and, R-6.15.4-010, *network access events: bearer pre-emption, loss of signal, failed registration* — the bearer-side event class a 23-June reconstruction needs, required of the MC service itself, not of the SIEM. At the security layer, TS 33.180 §10.1.2.3 fixes the security content per event (IPs, signalling identifiers, SIP URIs, HTTP URL, initiating/receiving parties, MIKEY/tokens, media-bearer IDs), with the user organisation responsible for encrypting, integrity-protecting, access-controlling and access-logging the logs (§10.1.2.4); the Rel-19 MC Recording Server is the 3GPP-native record function. Two bounds: 33.180 says the full range of loggable user events is out of its scope — the list is a floor; and §10.2 makes discreet monitoring and replay "required functions of a public-safety network" that "shall not be implemented … without explicit consent from all users" elsewhere — a rail deployment is elsewhere, and the consent is a design input, not an afterthought. The 22.280 logging follow-up noted at E-2026-09-19-07 is closed by this reading.** **Where the record lives at Stage 2, and where it does not (E-2026-09-19-13, TS 23.280 V20.4.0): Rel-19 added a recording and replay architecture — Recording server, Recording admin and Replay clients, reference points REC-1…REC-5, and a separate identity, the MCRec ID (at most one per user, distinct from the MC service IDs, valid in the home system only, "not valid in a partner system even if the MC service user … would migrate"). That is the 3GPP-native home for the §6.15.4 field set *for session communications*. §5.2.12 puts recording of "non-session based communications and non-communication activities" outside its scope, and V19.6.0 removed MCData recording from Rel-19 — so for the non-communication activities 22.280 R-6.15.4-006…-008 require (registration state change, alias (de)activation, regroups), for MCData, and for users migrated across systems, there is no Stage-2 architecture at Rel-20. That part of the post-incident record is the operator's to build, and it is the part a 23-June reconstruction needs most. The gap widened by one CR at Rel-20 (E-2026-09-19-14, TS 23.379 V20.1.0, SA#110 2026-01): the MCPTT Stage-2 parameter "configuration of metadata to log" was removed — the choice of *what* to log now has no Stage-2 home at all.** **The rail side confirms the shape (E-2026-09-19-19, UIC SRS v2.1 §22 / FRS v2.1 §14.3): in V2 the only mandatory log is the metadata of Railway Emergency Communications, "available to the FRMCS operations" (M, §22.3.1 — the successor of GSM-R's confirmation of high-priority calls); logging of all MCX communications, media recording, extraction and persistent storage are M-V3, and "recording of encrypted data is out of scope for FRMCS V2". On the user-equipment side FRS §14.3.1–.2 mandate O&M activity logs in V2 but make every field beyond the functional identity — location, timestamp, bearer and RF conditions, registered applications, radio and internal faults — M-V3. **⚠️ WHAT "ONE GATE" IS UP AGAINST — THE NATIONAL ATO RISK WORK EXCLUDES SECURITY BY DESIGN (added 2026-08-19, E-2026-08-19-07 — Braband, ATO-RISK).** The DZSF-commissioned **ATO-RISK** project, which sets the risk-acceptance criteria for automated driving on the *Eisenbahnen des Bundes* network and supplies ADR-004 with its five-step CSM-compliant procedure, states as a **scope condition (R4)** that its considerations relate to **functional safety per the CENELEC standards, and that no other safety aspects — "explicitly cyber security", occupational safety or fire protection — are within scope**; human performance is likewise excluded (**R5**) and handled in the separate **ATO-SENSE** project. **So the German programme's answer to the safety/security split is organisational: it runs them as different projects.** That is coherent with **E-2026-08-19-06** — safety and security cannot share a quantified risk calculus, because an attack's occurrence does not follow a stochastic process that yields a probability the way a safety hazard does. **The consequence for this ADR is direct: "one gate for change" is a governance claim, not a methodological one. The gate can and must be single — one classification, one change-control path, one freedom-from-interference analysis (ADR-011 / ADR-004) — but the EVIDENCE arriving at that gate comes from two methodologically incompatible analyses that the national research programme deliberately keeps apart, and neither the semi-quantitative Risk Score Matrix nor a THR can carry the security half.** This ADR must therefore state how the gate ADJUDICATES between them rather than assuming a common risk currency: the attack-graph route (E-2026-08-19-06) is the candidate for the security side, DIN VDE V 0831-103 for the safety side, and the reconciliation is a decision this ADR still owes. **The seam is the same one ADR-004's boundary sits on** — and it is why adopting the ATO-RISK procedure whole would silently drop the security half of a layer that is both security-relevant and human-facing.

**THE GATE'S ADJUDICATION RULE — ARCHITECTURAL HALF, DECIDED 2026-08-20 (closes action item 9's decision-shaped core; quantitative calibration remains blocked, see item 9b).**

1. **Which instrument carries which half.** The **security half** is carried by attack-graph threat analysis over abuse cases (the DZSF-published method, E-2026-08-19-04/-06 — open-source tooling, two-team inter-rater discipline). The **safety half** is carried by the CSM-compliant semi-quantitative route in the DIN VDE V 0831-103 lineage (structure known from Braband, E-2026-08-19-07; normative scales not held — any citation of -103 content says so).
2. **No common risk currency is sought — that is the decision, not a gap.** Following Heinrich ch. 8 (E-2026-08-19-12): the security side expresses its output **in the safety side's existing, already-certified vocabulary at the point of detection** — deletion · corruption · delay · unavailability — so an attack reaches the safety system as a hazard it is already designed to cope with. Where a control reacts at runtime, corruption is preferred to silent discard (the message still arrives; sequence and error counters keep continuity).
3. **The gate rule.** A security finding with no quantifiable probability enters the change gate as a **named hazard**, never as a competing risk number. It blocks a change exactly when the hazard it maps to would block that change under the safety calculus — and where it maps to no hazard the safety case knows, **that unmappable finding is itself grounds to escalate the change one class (ADR-011 scheme, escalation rule i)**, because an unclassifiable threat is an unbounded blast radius. Accepted security risks are recorded as accepted (E-2026-08-19-06), not silently dropped at the gate.
4. **Bounds, stated so this is not over-claimed.** Heinrich ch. 8 answers **runtime composition**; the transplant here is the *vocabulary principle only*. The **quantitative weighing rule** was re-based 2026-08-20 on free primary instruments after the owner decision **not to purchase DIN VDE V 0831-103/-104** — CSM-RA severity classes and targets on the safety side, engagement-defined attacker scales on the security side, mapped findings inheriting the hazard's severity class (item 9b; the un-held normative scales are a permanently accepted residual and no conformity with either document is claimed). And the method's own seam is inherited open: **secure update is out of its scope**, so the CRA-update-vs-change-control trade this ADR exists for is governed by the gate above, not resolved by the composition principle. The availability cost of fail-safe security reactions (E-2026-08-19-12 limb f) is charged to R3/R4 explicitly wherever the vocabulary principle is applied.

## Trade-off analysis

The governing trade is **conformance rigour + reuse vs process overhead**. Option A is cheapest and reproduces the 23-June mode (ungoverned change) with a security trigger, plus Art 64 exposure. Option C duplicates process and creates the two-regime hazard. Option B adds a CRA/NIS-2 overlay but **reuses ADR-011 (change-control), ADR-007 (test surfaces) and ADR-004 (boundary)** that must exist anyway — so the marginal cost is the classification + conformity overlay, and it keeps safety and security changes under **one gate**.

## Consequences

- **Easier:** R14 governed; PR16 treated; **PR13 mitigated** (CRA SBOM + security-update evidence); safety and security changes share one gate; NIS-2 reporting embedded in the SMS; the Q.752 detection layer does double duty for security.
- **Harder:** CRA conformity assessment + SBOM discipline across many PDEs and legacy elements; the **expedited actively-exploited-vuln path must still be gated** (tension between CRA Art 14 speed and SIL-4 rollback intolerance); support-period commitments for long-life rail assets — an end-of-life element (cf. the 1991 node) may lack CRA-conformant vendor support, re-raising **PR13/PR14**.
- **To revisit:** CRA delegated/implementing acts + harmonised standards as they land; **the Radio Equipment Directive + its cybersecurity delegated act vs FRMCS radio equipment (E-2026-08-15-53 — named by ERJU System Pillar alongside NIS 2/CSA/CRA; still unevidenced here)**; TS 50701 / IEC 62443 mapping **(and its successor: the ERJU SP spec is the stated reference system for IEC 63452)**; whether the oversight layer needs its own conformity-assessment tier; the residual verification gaps (E-2026-07-01-06).
